Cohort-unique 5-WEDGE non-overlap (vs Braintrust 1216)

  1. Continuous-improvement loop framing: HoneyHive frames the workflow as session → trace → dataset → evaluator → annotation → prompt/tool revision → production feedback → remediation → release. Braintrust leads with evals + observability as two lanes joined by traces; HoneyHive explicitly markets the closed loop. The replay schema must preserve the loop edges, not just the nodes.
  2. Human-in-the-loop + production feedback as first-class primitives: the launch post calls out human feedback and production iteration. The 22-field schema needs human_feedback_id, production_feedback_id, and annotation_queue_id as keys, not as free-text blobs.
  3. Prompt and tool revision history joined to the trace: every trace must reference the exact prompt_version_id, model_version_id, and tool_version_id that produced it. The replay must show what was live in production, not the latest dev revision.
  4. Remediation + release evidence: when a failure triggers a remediation, the schema must join the failure trace → the remediation action → the re-evaluation that approved the fix → the release that shipped it. This is the audit trail an incident reviewer will demand.
  5. Dataset–evaluator–annotation co-versioning: datasets, evaluators, and annotation queues must version together. If a dataset is replaced without versioning the evaluator that scored against it, the lineage is broken. The schema must keep dataset_version_id, evaluator_version_id, and annotation_batch_id as a triplet, not as three independent keys.

The five highest-priority evidence gaps

  1. Loop edge preservation: most observability stores the nodes (sessions, traces, datasets) but loses the edges (which dataset version produced which evaluator run, which evaluator run produced which prompt revision). The replay must carry edge provenance, not just timestamps.
  2. Prompt/tool/model version join at production time: the trace must point at the exact versions that produced it. If the trace stores only the trace ID, an incident reviewer cannot reproduce the production configuration.
  3. Human feedback + annotation as replayable keys: free-text feedback is not audit evidence. Each feedback row needs a stable human_feedback_id + annotation_batch_id + reviewer identity + timestamp + decision context.
  4. Remediation → re-evaluation → release chain: when a failure triggers a remediation, the chain must close. If the re-evaluation is missing, the remediation was unverified; if the release is missing, the remediation never shipped. Both edges must be exportable.
  5. Retention, deletion, and cross-tenant isolation: the export must include retention_policy_id, deletion_proof_id, and cross_tenant_no_bleed_invariant per row. Without these, the export cannot satisfy EU AI Act Art. 13 logging or SOC 2 CC6.1 logical access for the AI agent scope.

Procurement / incident-review questions the buyer will ask

  1. Can one production outcome join to its exact session, trace, dataset, evaluator, prompt, model, tool, and code revisions?
  2. Can automated scores, annotation queues, human feedback, and production signals be compared without losing tenant or release boundaries?
  3. Can a reviewer replay the continuous improvement loop from failure detection through diagnosis, remediation, re-evaluation, and deployment?
  4. Can retention, deletion, regional processing, and cross-tenant isolation be proven for traces, datasets, feedback, and attachments?
  5. Can HoneyHive export one control receipt that survives procurement, incident review, and AI-governance audit?
